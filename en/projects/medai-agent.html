01 · The problem

Turning free-form input into information the next stage can use.

This prototype handles medication information supplied as text, voice or images through a shared workflow and presents a readable report. I connected input interfaces, a medication-information API, role-specific LLM processing and the results UI.

02 · Processing flow

Connecting stage outputs from input understanding to the report.

The eight stages cover input understanding, medication recognition, background knowledge, detailed analysis, side-effect review, evidence explanation, contextual information and report generation. Outputs pass between stages, and FastAPI responses feed React summary and detail views.

These stages are LLM calls assigned different roles, not independent medical experts. Facts retrieved from the MFDS medication API must be distinguished from model-generated explanations.

What I verified

The prototype and demo connect input, lookup, generation and report display. Medical accuracy of the risk indicators and recommendations was not validated.

03 · Communicating the workflow

Presenting a multi-call workflow in a readable result screen.

The interface shows progress during processing and organizes the result into a summary, key points, cautions and detail. This helps users distinguish the workflow state from its output rather than reading an undifferentiated block of generated text.

04 · Learning & remaining work

The flow of information mattered more than the number of stages.

Building a system where drug names and early interpretations become later inputs highlighted the need to locate errors in the flow. The demonstrated result is the integration and UI; stage-ablation studies and medical-accuracy validation remain uncompleted.

Further evaluation should trace retrieved facts and generated explanations and measure how removing stages changes quality and latency. This is a validation plan, not a claimed quality improvement.
